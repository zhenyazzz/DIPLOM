# Архитектурные варианты и интеграция

**Связь:** REQ-PRE-05, REQ-INT-01..04, REQ-TECH-*, REQ-SEC-*, REQ-DB-*, REQ-DEP-01.  
**Ограничения планирования:** не предполагать обязательность микросервисов, Kafka, Kubernetes.  
**Статус:** варианты сравнены.  
**Выбор студента (17.10.2026, `proposed` → зафиксировать с рук.):** модульный монолит **core** + **2 сервиса вокруг** + фронт **React + TypeScript** (DEC-ARCH-01, DEC-ARCH-02).

---

## 1. Критерии сравнения

Сложность для одного студента (~до 14.12.2026); закрытие «≥2 компонента» и явной интеграции; тестируемость; демонстрируемость на защите; надёжность развёртывания вне IDE.

---

## 2. Альтернативы

| Вариант | Суть | Сложность | ≥2 компонента | Тестируемость | Для КР |
|---|---|---|---|---|---|
| **(а)** | Модульный монолит Spring Boot + Thymeleaf/HTMX | Низкая | Слабее (нужны внешние адаптеры/модули) | Высокая | Запасной |
| **(б)** | Spring REST + SPA (React/Vue) | Высокая (2 стека) | Естественно | Хорошая (контракт) | Только при сильном фронте |
| **(в)** | Веб-приложение (core) + отдельный calc-сервис REST | Средняя | Сильнее всего | Хорошая (контракт OpenAPI) | **Основной `proposed`** |
| **(г)** | Микросервисы | Очень высокая | Формально да | Сложнее | Отклонить |
| **(д)** | JavaFX + БД | Средняя | Нужен отдельный «второй» контур | Средняя | Слабее при ожидании веба |

**Риск формальной интеграции:** один jar с пакетами без сетевого/файлового обмена может быть оспорен. Бланк **допускает** «доступ к общей подсистеме данных» (REQ-INT-03) — но безопаснее показать **явный** сценарий: HTTP к calc **или** файловый импорт + внешний API (НБРБ/ERP-stub).

---

## 3. Рекомендуемые варианты

### Выбранный студентом контур (`proposed`, 17.10.2026) — монолит + сервисы + React

По сути это **гибрид (б)+(в)**: один основной backend (модульный монолит) и **ровно два** окружающих сервиса, фронт отдельно.

| Часть | Что делает | Зачем |
|---|---|---|
| **frontend** | React + TypeScript (SPA) | UI: заявки, импорт, расчёты, сценарии, отчёты |
| **core** (модульный монолит Spring Boot) | Пользователи/роли, заявки, сценарии, отчёты, оркестрация, PostgreSQL, Flyway, Security | Главная бизнес-логика и БД |
| **finance-service** | v1: тонкий приём CSV → валидация → JSON; «интересное» (Excel/НБРБ/stub) — позже | Явная «интеграция финансовых данных»; можно откладывать глубину |
| **calc-service** | МКА + оптимизация портфеля, OpenAPI, `BigDecimal`, без своей пользовательской БД | Явный второй расчётный компонент |

**Интеграции (для защиты):**  
1) browser → core (REST);  
2) core → finance-service (импорт/нормализация);  
3) core → calc-service (ранжирование/портфель).  

В ПЗ описать один **главный** сквозной сценарий (REQ-INT-04) + sequence (GFX-05). OpenAPI — минимум на calc и finance (REQ-TECH-04).

**Деплой:** `frontend` (build static / dev server для демо) + 3× Java jar **или** core+2 сервиса в Compose + PostgreSQL. Docker не обязателен (REQ-TECH-05).

**Правила, чтобы не утонуть:**
- Не плодить 4–5 микросервисов, Kafka, service discovery.
- БД пользователей/заявок — **только у core**; finance и calc — по возможности stateless (или минимальное хранение журнала импорта — решить на проектировании).
- Модули внутри core: `portfolio`, `security`, `integration-clients` — это «модульный монолит», не отдельные деплои.

**Критерий отката (если к ~05.11 нет сквозного вызова):** оставить React, но **влить finance в core** и оставить снаружи только **calc** (тогда компонентов всё равно ≥2: frontend/core и calc, плюс файловый импорт как интеграция). Не откатываться на Thymeleaf — студент знает React.

### Запасной (`proposed`) — упрощение выбранного контура

- React + **один** backend (core), внутри — модули finance и optimization.  
- «Второй компонент» для бланка: calc вынести обратно **или** явный внешний контур (файл + НБРБ/ERP-stub) с sequence.  
- Использовать, если два отдельных Java-сервиса съедают срок до 15.11.

## 4. Интеграция финансовых данных

| Механизм | Уместность | Заметки |
|---|---|---|
| CSV/XLSX | Must | OpenCSV/POI; журнал сессии импорта |
| ERP-stub (REST/JSON) | Should | WireMock/фикстуры «как будто учёт» |
| API НБРБ курсы | Could | [Ф+URL] https://www.nbrb.by/apihelp/exrates · `https://api.nbrb.by/exrates/...`; кэш + fallback |
| RabbitMQ и очереди | Нет по умолчанию | Только при необходимости (REQ-TECH-06) |

Свойства: идемпотентность, версия прогноза, частичный отказ с отчётом ошибок, атомарность принятия валидной пачки.

**GFX-08:** условно обязателен при заявленной внешней системе (НБРБ/ERP-stub) — тогда включить в комплект плакатов.

## 5. Оптимизационный движок

| Размещение | Плюсы | Минусы |
|---|---|---|
| In-process в монолите | Проще | Слабее нарратив «2 компонента» |
| In-process **внутри calc-сервиса** | Баланс | Нужен контракт и 2 процесса |
| Отдельный 3-й solver-сервис | — | Раздувание — **не делать** |

Синхронный расчёт при $n\sim 30$ — обычно достаточно; при долгих расчётах — статус job (`unresolved`, не обязателен). Воспроизводимость: сохранять входы, веса, версию метода, результат сценария.

Выбор библиотеки решателя — см. `mathematical-options.md` (DEC-MATH-02).

## 6. Безопасность (соразмерно REQ-SEC-02)

`proposed`: Spring Security (form-login для Thymeleaf **или** session для SPA); BCrypt; ≥3 роли RBAC; Bean Validation; CSRF для форм; внутренний токен/API-key core→calc; секреты вне git.  
HTTPS — желательно описать; для локального демо допустим HTTP с оговоркой в ПЗ.  
Не обязательно для КР: Keycloak, column-level encryption, полноценный SSO.

---

## 7. Хранение

`proposed`: **PostgreSQL** (сдача/демо); H2 — только unit/smoke при необходимости; **Flyway**; JPA для CRUD + явные запросы для ≥5 join (REQ-DB-07); деньги — `NUMERIC`/`BigDecimal`.  
Нормализация — обоснование 3НФ (REQ-DB-08).  
≥10 сущностей — из `domain-research.md`, без искусственных таблиц.
