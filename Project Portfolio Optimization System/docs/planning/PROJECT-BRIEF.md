## 2. Цель и задачи проекта

### Цель

Дать предприятию **воспроизводимый** инструмент отбора проектов в портфель при:

- нескольких критериях оценки (не только деньги);
- ограниченных ресурсах (прежде всего бюджет);
- финансовых данных из внешних выгрузок (CSV/XLSX);
- прозрачном объяснении «почему проект вошёл / не вошёл».

Система — **аналитическая поддержка решения**, не замена ERP, бухгалтерии, Гантта или табелей.

### Задачи (из предметной постановки)

1. Реестр проектных инициатив (карточки, статусы, зависимости).
2. Оценочная модель (критерии, веса, направление предпочтения) + расчёт интегрального балла (**SAW / взвешенная сумма**).
3. Импорт и публикация финансовых данных (CSV/XLSX → проверка → снимок).
4. Формирование портфельного сценария: кандидаты, бюджет и др. ограничения.
5. Оптимизация состава: **бинарный (0-1) выбор** проектов, максимизация суммы баллов при ограничениях.
6. Сравнение/выбор альтернативы, отчёт, аудит; роли и доступ.
7. UI (React) + документированные API; тестирование; деплой вне IDE.

### Что сознательно НЕ входит в ядро

- Детальный Гантт / CPM / табели / пофамильное управление людьми.
- Полноценная ERP / realtime-бухгалтерия.
- Kafka, K8s, ESB «ради галочки».
- Финансовые портфели ценных бумаг (не тот PPM).

## 3. Проблема AS-IS → TO-BE (кратко)

**AS-IS:** разрозненные Excel, субъективный отбор, веса не зафиксированы, слабая воспроизводимость, долгий пересчёт при урезании бюджета.

**TO-BE:** единая карточка инициативы → импорт финансов с протоколом ошибок → единая МКА (SAW) → оптимизация под бюджет/зависимости → сценарии «что если» → утверждение с аудитом.

**Ключевой процесс для демо:** «Формирование и утверждение портфеля на бюджетный период».

## 6. Математика (`proposed` в planning)

Цепочка v1:

1. **Финансы** → показатели (минимум NPV из потоков; BigDecimal only).
2. **МКА** → **SAW** (min-max нормализация + веса; без silent zero на пропуск).
3. **Оптимизация** → **0-1 knapsack-like** под бюджет (+ зависимости/mandatory/forbidden).

Алгоритмы для DOC-437: (1) финансы NPV/…, (2) SAW, (3) 0-1 отбор.

`unresolved`: TOPSIS позже в том же calc; решатель (своя ДП / ojAlgo / OR-Tools).

## 7. Ограничения бланка ИИСиК (что система обязана закрыть)

- ≥15 ФТ, из них ≥9 не-CRUD; ≥3 роли; ≥3 спец. бизнес-операции; отчётность; поиск/фильтр/сорт.
- AuthN/AuthZ; РБД ≥10 связанных таблиц (обоснованно), 3НФ в общем случае.
- **≥2 взаимодействующих программных компонента** + явная интеграция (не «пакеты в одном jar»).
- Модульные + интеграционные тесты; UI-сценарии; деплой вне IDE.
- Стек свободный; OpenAPI/Docker — желательно; микросервисы/Kafka — только если нужно.
- Сквозной сценарий: UI → логика → данные/интеграция → результат.

### Core — feature `001-user-auth` (сделано)

- Hybrid auth: **access JWT** в JSON + **opaque refresh** в HttpOnly cookie.
- Endpoints: register / login / refresh / logout; `GET /users/me`; admin users (list, change role, block).
- Роли: 4 enum’а выше; `@PreAuthorize` на admin.
- BCrypt; refresh-сессии в БД (hash); ротация refresh; block → revoke all.
- Flyway: users + refresh_sessions; seed Admin (`admin@portfolio.local`).
- Пакеты impl: `auth/`, `identity/`, `shared/`.
- Зависимости: `common-security` (валидация JWT), `common-web` (включён `@EnableCommonWeb`, CRUD-ресурсов ещё нет).

## 10. Технические инварианты (не ломать)

1. Деньги / веса / scores — только **`BigDecimal`**, не `double`/`float`.
2. Issuance JWT — в **core**; validation — **`common-security`** (общий secret).
3. Core **не** считает SAW/knapsack локально (constitution) — делегирует **calc** по HTTP.
4. Парсинг CSV/XLSX — **finance** (или временно в core при откате).
5. Вызов calc/finance: версионированный REST, таймауты, явные ошибки (не silent empty portfolio).
6. YAGNI: без Kafka/K8s/лишних модулей.
7. Тесты обязательны для фичи (unit + integration; IT часто нужен Docker/Testcontainers).
